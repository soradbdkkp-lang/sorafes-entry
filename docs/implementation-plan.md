## 順序と公開条件

依頼のPhase順序を維持する。まずフォームと入力整合を固め、保存先を決めてから認証・重複検出を追加することで、未確定の外部構成へUIを密結合させない。ただしPhase 3の保存設計ではPhase 4・5に必要な識別・更新・競合への対応を先に考慮する。

Phase 3の保存成功だけでは公開受付の準備完了としない。初回公開から実応募を受け付けるため、Phase 4の発行・編集とPhase 5の重複防止を本番保存先・通信方式へ統合してから受付を有効化する。公開時期は準備と検証の完了後に決める。

早期公開に向けた最小の残作業は、公開URLと通信方式の決定、試験環境から分離した本番保存先と所有者権限の設定、正式締切の保存側強制、Phase 4の発行・編集とPhase 5の保存時重複判定の統合、架空データだけによる本番同等構成の往復試験、応募者向けの情報取扱い・注意事項の確認、受付停止と障害時の手順の確認である。試験用 `testOnly` 契約やローカル開発サーバーのAPIをそのまま本番受付に使わない。新しいGoogle保存先・配備や共有設定の変更は、対象と権限を具体的に示して確認してから行う。

2026-10-11、本番候補の保存・編集・重複判定を試験コードから分離し、設定不足時に閉じるApps Script用ソースと公開前ローカルプレビューを追加した。本番用Google保存先3ファイルとApps Scriptを作成し、生成物と初期停止設定を反映した。3保存先は当面所有者限定とする。受付番号接頭辞検査を修正してバージョン2へ再配備し、架空データの新規保存、同一処理再確認、重複拒否、誤コード拒否、3保存先の内容、停止復帰を確認した。結果は [本番保存経路のGoogle実環境検証](production-google-verification.md) を参照する。

同日、保存経路の検証用としてReact画面をHTML Service用の単一HTMLへ生成し、`google.script.run` で同じWebアプリ内の本番保存処理を呼ぶ構成を実装・配備した。保存試験の完了後、正式公開では参加者が `script.google.com` を直接開かず、Cloudflare Workers上の `sorafes-entry` で応募を完結し、同一オリジンAPIからApps Scriptを呼ぶ方式を採用した。Worker中継、本番クライアント、本番文言、完了画面、再送回復をローカル実装し、自動テスト・本番ビルド・Wranglerローカル結合を確認した。次工程はCloudflare実環境設定と、受付停止状態での公開前確認である。
