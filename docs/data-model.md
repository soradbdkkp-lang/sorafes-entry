# 概念データモデル

> 2026-10-11現在地の補足：以下の初期設計・Phase 4試作時の「未確定」「未実装」は当時の記録を含む。本番用の認証・履歴・応募一覧3ファイルは所有者限定で作成済み。受付番号は `FAC-2026-`＋6桁連番、短時間制限は全体200要求/分・同一受付番号の認証失敗5回/分を採用済み。本番候補の保存・編集・重複判定は実装し、Google保存経路の限定的な架空データ試験後に受付を停止した。正式公開方式はCloudflare Workers＋同一オリジン `/api/entry` で、HTML Serviceは運営検証用として残す。リンク閲覧可能という記述はPhase 3・4の試験環境だけを指し、本番3ファイルには適用しない。現在の具体構成は [本番設定](production-apps-script-setup.md)、検証済み範囲は [Google検証記録](production-google-verification.md)・[ローカル再検証](cloudflare-handoff-verification.md)を参照する。追加共有、紛失時の本人確認・運営対応、正式URL、受付開始は未決定・未実施のまま保持する。

これは概念と責務の整理であり、実DB、スプレッドシート列、型定義、APIの最終確定ではない。大会固有値は共通処理から分離する。

| 概念 | 責務・主な情報 |
| --- | --- |
| Tournament | 大会識別、ブランド・名称、開催日、募集期間、定員、応募形式、質問設定、注意事項、公開状態。未確定日程を確定値に置き換えない |
| Application | 1大会への1応募。応募形式、応募人数、チーム名（該当時）、代表者参照、参加可能時間、受付・更新の状態 |
| Player | 応募内の各メンバー。名前、X ID、環境とその他詳細、ゲーム内ID、総プレイ時間、担当可能ロール。全大会共通の個人アカウント化は前提にしない |
| TournamentHistory | 各プレイヤーのDIF / DCK / その他大会の経験有無と条件付き実績。その他大会は複数の大会名・回数を保持 |
| KillerSelection | キラー担当可能者の専任 / 兼任、使用可能キラー複数、最得意キラー1体 |
| KillerCatalog | UIと分離したキラー一覧。初回大会はVol.1のキラー別カードからスカルマーチャントを除いた43体。固定IDと表示名を保持し、更新時は大会ルールとの照合が必要 |
| EditCredential | 応募編集の認証責務。受付番号との対応、編集コードの検証情報を扱う。公開応募データと分離 |

## 関係と整合

- Tournament 1件にApplicationが複数。Applicationは必ず1大会に属する。
- Application 1件にPlayerが応募人数分。代表者はそのPlayerのうち1名。個人応募では唯一のPlayerを参照する。
- Playerごとに大会実績の経験回答を持つ。経験なしと未回答を区別し、経験なしを実績の欠損と取り違えない。その他大会の明細は0件以上。
- 経験ありなら各回数に数値または明示的な「不明」を持つ。不明、0、未回答を区別する。その他大会経験ありでは大会名付き明細が1件以上必要。
- Playerのキラー担当可能が有効な場合にKillerSelectionを持ち、キラーの選択はKillerCatalogを参照する。
- KillerSelectionは専任 / 兼任、使用可能1体以上、使用可能一覧に含まれる最得意1体を持つ。サバイバー4人応募では全員サバイバーとして扱い、KillerSelectionは持たない。
- チーム応募ではキラー担当可能なPlayerが1名以上必要で、応募人数の範囲内で追加の上限を設けない。キラー応募ではキラー担当必須で兼任可否を保持する。
- 全Playerの基本情報・X IDは必須。応募時点でXアカウント作成から3か月以上の条件は運営が手動確認する。月数の計算方法・具体手順は未確定。作成日の保存項目を追加しない。
- 入力の一時保持と確認データを分離する。確認データは現在の応募人数・形式・回答で有効な項目のみをコピーし、X IDの前後空白と先頭@、ゲーム内IDの前後空白を除く。対象外の詳細は含めない。保存連携は後続フェーズ。
- 応募形式の識別は人数とは別に保持し、4人セットと4人チームを区別する。
- 参加可能時間はApplicationに属し、Playerごとに重複保存しない。
- 公開状態、募集状態、応募受付、当選、最終チーム編成は別の概念。具体的な状態一覧や編成モデルは未確定。

## 保存連携の境界

将来Google Sheets / Apps Script等を候補とする。フォームから概念モデルへの変換、検証、保存アダプターを分離し、シート行番号を画面の識別子や編集権限として利用しない。応募と複数プレイヤー・実績の対応を安定した識別子で表せる構造を検討するが、識別子の生成方式・列配置は未確定。

複数の情報をまとめて保存する際の途中失敗、再送、同時更新、重複競合への対処をPhase 3以降で設計する。保存成功を確認してから受付完了とする。受付番号だけを秘密として扱わず、編集の検証は保存側で行う。

編集コードは実値をGit、クライアント配信設定、通常ログ、公開シートへ保存しない。推測困難性、検証情報の保管（ハッシュ化等の候補）、試行制限、再発行方式はPhase 4で確定する。具体的なアルゴリズム・正式フォーマットは未確定。

2026-10-08採用：編集認証情報は応募シートとは別の非公開ファイルで管理する。具体的なファイル・権限・検証方式は未確定。紛失時の自動再発行は行わず運営相談とする。全応募項目を編集可能とするため、応募識別子は形式・人数の変更でも同じ応募を識別できる設計とする。版管理と改訂履歴の保存案・共有範囲などの未確定事項は `phase4-design.md` を参照する。

## 重複とアクセス

X ID・ゲーム内IDは重複照合の候補であり、認証情報ではない。2026-10-09採用：同じ大会の最新確定応募を照合し、認証済み編集では自分の応募を除外する。X IDは前後空白・先頭`@`・英字大小をそろえ、ゲーム内IDは前後空白だけを除いて`#`以降と文字大小を保つ。一方だけ一致した場合も重複候補として保存を保留する。単純な名前一致で同一人物と断定しない。詳細と未確定の本番照会方式は [phase5-design-proposal.md](phase5-design-proposal.md) を参照する。

本番の保存先は認証・履歴・最新応募一覧の3スプレッドシートに分離する。応募情報は削除せず保持し、3ファイルはいずれも運営アカウント限定とする。当面は所有者のみ閲覧・編集可能とし、追加する運営アカウントは未指定。編集検証情報・秘密情報・抽選内部情報は応募一覧とフロントエンドへ配信しない。取得項目は `requirements.md` の範囲に限定する。Phase 3・4の試験用共有ファイルは本番保存先に使用しない。
