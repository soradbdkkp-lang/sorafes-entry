## 確定済みの前提

- 受付番号と推測困難な編集コードを用い、X IDだけでは編集を許可しない。
- 応募情報シートはリンクを知っている全員が閲覧でき、保存された情報は削除しない。
- 編集認証情報・秘密情報は共有応募シートから分離する。非表示タブを秘密情報の保管先にしない。
- メールアドレス・Discord ID・電話番号・本名・住所を追加取得しない。
- 保存成功と当選を区別し、応募多数の場合は「応募多数の場合は抽選」と表示する。
- Phase 3のTEST保存IDは正式受付番号ではない。既存試験行は変更しない。

## 採用した運用（2026-10-08）

1. 編集期限は正式応募締切と同じ日時。2026-10-09に正式締切を2026年10月24日23:59（日本時間）と決定した。
2. 応募形式・人数・メンバーを含む全応募項目を編集可能とする。更新時に変更後の応募形式の条件をすべて再検証する。
3. 編集コード紛失時は自動再発行せず [運営Xアカウント](https://x.com/sora_kkp_game)へ相談。本人確認・運営が修正できる条件は未確定。
4. 認証情報は応募シートとは別の非公開ファイルへ保存し、現在のApps Script所有者のみ閲覧・編集可能とする。架空データ専用の試験ファイルは作成・検証済み。本番用ファイルは未確定・未作成。
5. 修正前の応募情報を含む変更履歴は削除せず、運営限定の非公開ファイルへ保存する。認証情報の所有者限定権限を守るため、認証ファイルとは別ファイルとする設計。閲覧を許可する具体的な運営メンバーは未指定。

### 比較検討の履歴

以下は採用理由の記録。4項目ともA案を採用し、B案は採用していない。

| 項目 | A案 | B案 | 推奨と理由 |
| --- | --- | --- | --- |
| 1. 編集期限 | 正式応募締切と同じ日時 | 応募締切後にも別の編集期限を設定 | A。締切後の名簿・対戦準備を安定させやすい。当時の正式締切日時は未確定で、2026-10-09に決定済み |
| 2. 編集範囲 | 応募形式・人数・メンバーを含む全応募項目 | 応募形式・人数・メンバーの追加削除を固定し、登録済みメンバーの情報・代表者・チーム名・時間回答を編集可能にする | A。入力間違いやメンバー変更をフォーム内で解決できる。全条件の再検証とPhase 5の重複確認が必要 |
| 3. 編集コード紛失 | 自動再発行せず運営相談 | 運営が本人確認後に再発行できる機能を設ける | A。公開されるX IDや受付番号を使った不十分な本人確認を避けられる。ただし相談先・確認方法・運営が修正できる条件は別途決定が必要 |
| 4. 認証情報の保存先 | 応募シートとは別の非公開ファイル | シート以外の非公開保存サービス | Aを第一候補。現行構成に近い。ただし所有者・編集者・ファイル作成の承認と、別ファイル保存の途中失敗対策が必要。共有応募シート内には置かない |

B案の編集範囲でも、名前・X ID・ゲーム内IDの修正によって実質的にメンバーが入れ替わる可能性がある。本人情報の訂正と交代の区別は入力だけでは保証できず、B採用時は運営ルールを追加で決める。

紛失時の運営相談は再発行や修正を保証する意味ではない。確認方法が決まるまでは、受付番号・X ID・シート掲載内容だけで再発行しない。新規応募し直しを標準対応にすると重複につながるため、自動案内しない。

## 画面と保存の提案

技術具体案は [phase4-technical-proposal.md](phase4-technical-proposal.md) を参照。送信前にコードを生成・保存する基本方式を採用した。受付番号は保存成功後に受領する。正式フォーマット等の詳細と実装承認は分けて扱う。

### 初回受付

入力 → 全体確認 → 編集コード生成・手元への保存確認 → 保存 → 正式受付完了。受付番号と編集コードを別々に表示し、コピー操作と手元への保存案内を付ける。自動メール送信は追加しない。編集コードはURL・共有シート・通常ログへ含めない。

受付番号は大会ごとに識別できる形式を候補とし、行番号とは分離する。文字列形式・採番方式は未確定。編集コードは十分な推測困難性を持つ方式を選び、生成方法・長さ・検証方式は実装前に確認する。既存文書の短い例示コードを、そのまま正式仕様にしない。

保存後の応答切断に備え、コードを送信前に本人が保存する基本方式を採用した。非秘密の再送識別IDだけで保存結果や編集コードを取り出せる設計にはしない。認証済みの再確認手段はローカルで実装・検証済み。Google実環境の本番対応は未実装。

### 既存応募の編集

編集入口 → 受付番号・編集コード入力 → 保存側の認証 → 現在の応募内容 → 修正 → 全体確認 → 更新保存 → 更新完了。

認証前にはフォームAPIから応募内容を返さない。認証失敗は番号不存在とコード不一致を区別しない案とし、試行制限・一時認証の有効期限・失効方法は未確定。共有シートは既にリンク閲覧可能なので、この認証が応募情報全体の非公開を保証するとは説明しない。

期限判定は保存側で行い、編集画面を開いた時点だけでなく更新時にも確認する。正確な日時とタイムゾーンは大会設定で管理する。新規受付停止と編集停止を別に扱うかも、運用決定に合わせて整理する。

保存済みの版を読み込み、更新時に版が一致しなければ上書きせず、最新内容の再確認を案内する。通信失敗時は入力を保持し、同じ更新操作の再送で二重更新しない方式を設計する。

## データと失敗への備え

応募内容・安定した応募識別子・受付番号・版・更新日時と、非公開のコード検証情報・認証状態・再送管理を分離する。編集コードの平文を恒久保存する方式は採用前に再検討し、具体的な暗号方式や実行環境の乱数生成能力は未確定として扱う。

「保存された情報は削除しない」を踏まえ、原本と改訂内容を非公開の履歴ファイルへ追記し、最新の確定版を識別できる方式を提案する。履歴は運営限定の非公開保存とすることをユーザー確認済み。古いX ID等の修正前情報が残ることを応募者へ説明する必要がある。秘密情報は履歴にも載せない。

別ファイルへの書き込みは一括で成功すると仮定しない。認証情報のみ保存、応募情報のみ保存、保存後の応答切断を区別し、処理識別子・処理中／確定状態と再送で整合を回復する案を具体化する。全必要情報の保存が確認できるまでは受付完了としない。孤立した途中データを削除して回復する方式にはしない。

コード失効・再発行を採用する場合は旧コードを無効にし、履歴保持と認証有効性を分ける。コード原文や秘密の回復情報を通常ログ・Git・ブラウザ配信設定に残さない。

## 実装前の条件と検証案

運用4項目と権限の基本方針は採用済み。コード生成・検証・初回再確認はローカルと独立したGoogle試験環境で架空データを使って検証した。正式締切と紛失時の相談先は決定済み。本人確認・運営対応条件、本番用の非公開ファイル・履歴閲覧メンバー、正式試行制限、本番通信方式は残る。試験用Google構成と停止状態は `phase4-google-verification.md` を参照。

### 当初の作業順序（履歴）

1. 非公開認証ファイルの所有者・編集者と、更新履歴の閲覧範囲を確認する。共有応募シートへの保存項目を決める前提になる。
2. 初回応答切断でも編集コードを安全に受領できる方式、認証・再送・版管理・途中保存回復の仕様を具体化する。非秘密の処理IDだけで認証を省略しない。
3. 架空データでのローカル検証範囲を提示し、Phase 4実装の承認後に実装する。当時は正式締切が未確定だったため、本番の受付・編集を有効にせず、試験用日時と区別した。
4. Google側の認証ファイル作成・設定は対象と権限を確認した後に行う。既存試験行や応募シートの共有設定は変更しない。

上記のローカル実装と独立したGoogle架空データ試験は承認を得て実施済み。以降の本番構成やPhase 5の実装を承認した意味ではない。

実装後は架空データで、発行と保存内容照合、認証失敗での非開示、締切境界、全形式の更新再検証、古い版の拒否、同時更新、同じ操作の再送、両保存先の途中失敗、初回応答切断後のコード受領、認証情報が共有シートへ混入しないことを確認する。Phase 5未実装時点では重複防止が完成したと表示しない。本番受付・公開は別途承認が必要。
