# 要件

## 共通システム

そらふぇす配下の大会に共通のエントリー基盤を提供する。初回はふろぐ Assemble Cup。ふろぐCup、派生大会、特殊ルール大会でも大会設定を差し替えて再利用する。

大会設定として、大会名、開催日、募集期間、定員、応募形式、取得するプレイヤー情報、大会実績・キラー情報の取得有無、注意事項、参加可能時間の質問、公開状態を扱う。以下の5形式は初回大会の設定であり、全大会に固定しない。任意の特殊ルールへ無制限に対応する仕様は現段階で確定しない。

## 応募形式

| 形式 | 人数 | 編成・代表者 |
| --- | --- | --- |
| キラーとして応募 | 1名 | 本人が連絡代表者 |
| 1人で応募 | 1名 | 本人が連絡代表者 |
| 2人で応募 | 2名 | 原則分割しない。代表者1名を選択 |
| 4人で応募（サバイバー4名） | 4名 | 原則分割しない。キラー担当者は後から運営が編成。代表者1名を選択 |
| 4～6人のチームで応募 | 4 / 5 / 6名から選択 | チーム名必須。代表者1名を選択 |

4人セットと4人チームは異なる応募形式として保持する。フォームだけで編成の最終確定を行わない。

応募形式ごとのロール条件は以下とする。

- キラーとして応募：キラー担当必須。サバイバーとの兼任可否も取得する。
- 4人で応募（サバイバー4名）：全員をサバイバー担当として扱い、キラー情報は質問しない。キラー担当者は運営が後から編成する。
- 4～6人チーム：キラー担当可能者1名以上を必須とする。キラー担当可能者の人数に追加の上限を設けない（応募人数の範囲内）。最終的な担当と、サバイバーを含む試合時の構成条件は別途未確定。

## 連絡・個人情報

代表者は応募メンバーから1名を選ぶ。全員のX（Twitter）IDを必須とする。当選者へ代表者XアカウントのDMで大会Discordサーバー招待URLを送付する運用を想定する。自動DM送信は今回の範囲外。

全員のXアカウントは応募時点で作成から3か月以上経過していることを条件とする。フォームで条件を案内し、運営が手動確認する。月数の計算方法・手動確認の具体手順は未確定。作成日を追加収集せず、外部APIによる自動確認は行わない。

Discord ID、メールアドレス、電話番号、本名、住所、その他大会運営に不要な個人情報は取得しない。

## プレイヤーごとの情報

- プレイヤー名、X（Twitter）ID、プレイ環境、ゲーム内ID、Dead by Daylight総プレイ時間、担当可能ロールを全員分必須とする。応募形式で固定されるロールは入力操作を省略し、確認画面で明示する。
- プレイ環境は **Steam / PlayStation / Nintendo Switch / その他** の4択。「その他」の場合だけ具体的な環境の追加入力を必須とする。
- X IDは前後の空白と先頭の@を除いて確認データに整形する。@の有無はどちらも許容し、整形後の空欄は不可。厳密な文字種・長さの制約は未確定。
- ゲーム内IDは `#` 以降も含めて入力する。前後の空白を除き、#の前後が空でないことを確認する。その他の文字制約は未確定。
- 総プレイ時間は複数プラットフォームの合計のおおよその時間でよい。0以上の有限の数値を必須とし、小数も許容する。
- 担当可能ロールは「サバイバー」「キラー担当可能」を基本とする。複数選択等の具体UIは未確定。

キラー担当可能者だけ、キラー専任 / サバイバーとの兼任可能の選択、使用可能キラー1体以上（複数選択可）、最も得意なキラー1体を必須とする。最得意キラーは選択した使用可能一覧から選ぶ。「使用可能」は大会で実際に出せる程度に使用できること。キラー一覧はUIと分離する。初回大会は[ふろぐCup Vol.1のキラールール下部「キラー別カード」](https://soradbdkkp-lang.github.io/dbd-tournament-site/frogcup-vol1/pages/killer-rules.html)の44体を参照し、スカルマーチャントを除く43体を使用可能一覧とする。フォームの収録名と固定IDは `src/config/killers.ts` に置く。今後の実装追加や大会ルール変更による一覧更新は、公開前に運営が確認して反映する。

## 大会実績

各プレイヤーにDIF、DCK、その他大会それぞれの経験有無を先に質問する。

| 分類 | 経験ありの場合だけ取得 |
| --- | --- |
| DIF | 出場回数、優勝回数、準優勝回数 |
| DCK | 出場回数、優勝回数、準優勝回数 |
| その他大会 | 大会名、出場回数、優勝回数、準優勝回数。複数大会を追加可能 |

経験有無は各分類で必須回答。「あり」なら出場回数は1以上の整数、優勝・準優勝回数は0以上の整数、またはそれぞれ明示的な「不明」で必須回答とする。「不明」を0や未回答と同一視しない。数値が分かる場合、優勝・準優勝の各回数は出場回数以下とする。両者の合計では制限しない。その他大会は「あり」なら1件以上を入力し、各大会名を必須とする。経験なしの場合は詳細を表示・送信しない。

## 条件変更と確認画面

人数・応募形式・条件回答を変えても入力は画面内で一時保持する。確認データには現在の人数と形式で有効な項目だけを含める。対象外メンバー、チーム形式以外のチーム名、その他以外の環境詳細、対象外のキラー詳細、経験なしの実績詳細を除外する。入力チェックも有効な項目だけに適用する。確認画面から各セクションを修正し、全体を再チェックして確認画面へ戻る。

## 参加可能時間

応募単位で1回だけ必須回答として取得する。複数人の場合は全員の予定を確認して回答する。

- 16:00開始でも参加可能
- 18:00以降の開始を希望
- どちらでも問題ない

回答前に「応募チーム・対戦方式によっては試合開始が16:00になる場合があります」と案内する。これは希望・参加可否の回答であり、正式開始時刻の確定ではない。「18:00以降の開始を希望」は18:00以降の試合開始を保証しない。希望と実際の予定が合わない場合の運営対応は未確定。

## 受付・修正・重複

正式公開画面はCloudflare WorkersからReact + Viteの静的資産と同一オリジンの `/api/entry` を提供し、Workerが裏側のApps Script `doPost()` へ転送する。参加者は `script.google.com` を直接開かず、本番サイト内で入力・確認・正式送信・完了まで行う。Apps Script URLはCloudflareの `SORAFES_PRODUCTION_APPS_SCRIPT_URL` Secretだけに保存し、ブラウザ、`VITE_` 変数、リポジトリ、ログ、応答へ含めない。詳細は [cloudflare-deployment.md](cloudflare-deployment.md) を参照する。

正常保存された確定応答だけを受付完了とし、`FAC-2026-...` を表示する。受付停止、保存失敗、重複、認証失敗、版競合、不正応答、操作ID不一致を成功扱いしない。結果不明時は入力と同じ操作IDを保持して再確認し、別応募として再送しない。

受付後も正式締切まで修正可能とする。初回送信前に推測困難な編集コードを生成し、本人が手元へ保存してから送信する。受付番号は保存側で採番し、保存成功後に受領する。受付番号は `FAC-2026-` に6桁連番を続ける。編集には受付番号・編集コードによる確認を必須とし、X ID・ゲーム内IDだけでは編集できない。基本方式は `phase4-technical-proposal.md` を参照。本番保存処理は実装済みで、架空データによるGoogle実環境の新規保存・同一処理再確認・重複拒否・認証失敗を確認済み。検証後は受付停止へ戻している。

2026-10-08採用：編集期限は正式応募締切と同じ日時とし、応募形式・人数・メンバーを含む全応募項目を編集可能とする。更新時は変更後の応募条件を再検証する。コード紛失時は自動再発行せず運営相談とする。認証情報は応募シートとは別の非公開ファイルへ保存する。正式締切は2026年10月24日23:59（日本時間）、運営相談先は [@sora_kkp_game](https://x.com/sora_kkp_game)。本人確認・運営対応条件は未確定。本番認証・履歴・応募一覧の3ファイルは作成済みで、当面は所有者限定とする。追加する運営メンバーは未指定。詳細と未確定の技術案は [phase4-design.md](phase4-design.md) を参照。

同一フォーム内では入力中にX ID・ゲーム内IDの重複候補を表示する。既存応募とは保存ボタンを押した時に保存側で照合し、確定まで同じ排他範囲で処理する。入力中の外部照会は行わない。既存応募で両方一致した場合は「このプレイヤーはすでにエントリーされています。」、一方だけ一致した場合は「重複の可能性があります。入力内容を確認してください」と表示し、入力の確認・修正や認証済みの既存応募編集へ誘導する。既存応募の内容は編集認証前に開示しない。2026-10-09採用：同じ大会の最新確定応募を対象とし、認証済み編集では自分の応募を除外。X IDは前後空白・先頭@・英字大小をそろえ、ゲーム内IDは前後空白だけ除いて#以降と大小を保つ。一方だけの一致も候補として保存を保留する。本人でない場合は [運営Xアカウント](https://x.com/sora_kkp_game)へ相談できるよう案内する。運営の判断手順・例外条件、照会制限の正式値は未確定。詳細は [phase5-design-proposal.md](phase5-design-proposal.md)。本番Google環境で、両方一致する別新規送信が保存前に `DUPLICATE` で保留され、受付番号・保存行を追加しないことを確認済み。

## デザイン要件

視覚・操作設計の正本は [DESIGN.md](../DESIGN.md)。既存dbd-tournament-siteの資料は確認済みで、正しい参照パスと適用範囲は同書に記録する。

ふろぐCup Vol.1の構造・雰囲気・UI設計思想を参考にした派生デザインとする。暗色・高コントラスト、情報を見つけやすいレイアウト、カード型UI、見出し階層、スマートフォン優先、色だけに依存しない状態表示、過度な演出の抑制、可読性・操作性の優先を共有する。

sorafes-entryは黒～濃いグレーの無地背景、白文字中心、緑の主要アクセント・ボタン・フォーカス・選択状態、フラットでシンプルなフォームUIを採用し、エントリーフォームの操作性を最優先する。背景柄、森、霧、粒子、筆跡、大きなカエル等の装飾を使用せず、AI生成感の強い装飾を避ける。

既存Vol.1のコーラル系アクセントは継承しない。同一「そらふぇす / ふろぐ」系サイトとして共通性を維持しながら、エントリーシステムの識別性を持たせる意図的な差分とする。

## 保存情報の保持と共有

2026-10-11確認：編集認証情報の非公開ファイルは現在のApps Script所有者のみ閲覧・編集可能とする。変更履歴は運営限定の別の非公開ファイルへ保存し、修正前情報も削除しない。本番応募一覧も運営アカウント限定とし、当面は所有者のみ閲覧・編集可能とする。追加する具体的な運営メンバーは未指定。

スプレッドシートに保存された応募情報は削除せず、大会開催日後も保持する。大会開催日を削除期限にせず、自動削除を設けない。

本番の応募情報シートは運営アカウント限定とし、リンクを知るだけでは閲覧できない設定を維持する。秘密情報・編集コード等の編集認証情報・抽選内部情報は応募一覧へ含めない。フォームや応募APIに一覧取得機能を追加しない。Phase 3・4の試験で使用した既存ファイルの共有設定は過去の試験条件として維持し、本番設定へ継承しない。構成案は storage-integration.md と production-apps-script-setup.md を参照する。
