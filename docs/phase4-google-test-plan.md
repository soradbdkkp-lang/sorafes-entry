## ローカル側で準備する変更

共通の入力検証と認証・再送・版管理を利用し、3保存先への書き込みアダプターを追加する。ローカル試験用の失敗注入APIを外部公開するApps Scriptへそのまま移植しない。

Phase 4専用のサーバー側試験設定を既存のPhase 3設定とは別に用意する。URL・ファイルIDは非秘密の設定、試験キーと実際の編集コードは秘密として扱う。既存 `.env.local` の他の設定を消さず、除外を確認する。キーをブラウザへ配信しない。キーの新設・既存キー利用は配備前に確認し、チャットへ値を貼るよう依頼しない。

新規試験APIは試験モード・架空データ確認・保存側検証を要求し、設定不足時は受付・編集を閉じる。試験受付番号は本番と区別できる接頭辞を使い、本番の正式形式を確定しない。試験期限は本番締切とは別の明示的な設定にする。受付と更新は保存側でも期間を確認する。

Apps Script作成・Google権限承認・配備で所有者の操作が必要な場合は、貼り付けるコードと設定項目を先に準備する。ログインや権限承認の完了を、ローカルのビルド成功だけで推定しない。

## 実環境での試験順序

1. 承認後に対象ファイル・タブと権限を確認し、既存 `シート1` とPhase 3試験タブの確認範囲を記録する。全データが不変と報告するなら全使用範囲の前後照合が必要。
2. 新規非公開ファイルと専用タブ・独立Apps Scriptを準備する。認証ファイルのリンク閲覧が許可されていないことを確認する。
3. Googleアダプターを模擬環境で検証し、権限拒否、各書き込みの前後失敗、flush後の応答切断、排他・再送を確認する。既存26件のテストも実行する。
4. 所有者の試験用配備後、架空データのみで全5応募形式・チーム4／5／6名を保存・読込・編集し、3保存先を照合する。
5. 同一送信・更新の再送、版競合・同時更新、誤コード、再読み込み後の再確認を検証する。通信切断はローカル中継で行い、既存Googleシートの権限を失敗注入目的で変更しない。
6. 認証情報が共有応募タブや運営向け履歴へ混入していないことを確認し、確認範囲と未検証事項を記録する。試験データは削除しない。
7. 試験終了後、新規Phase 4試験APIを停止し、停止後の追加保存・更新拒否とデータ保持を確認する。Phase 3停止設定は変更しない。

## 実施結果

独立した `apps-script/phase4-server.ts` と `scripts/build-phase4-apps-script.mjs` を追加し、`apps-script/phase4-generated/Code.gs` を生成した。旧Phase 3用Code.gsとは別のファイルである。専用ローカル中継と `/?phase4=google` の画面を追加し、保存・認証読込・編集・再読み込み後の回復を実環境で確認した。Google模擬テストと設定は [phase4-google-setup.md](phase4-google-setup.md)、実測と残る限界は [phase4-google-verification.md](phase4-google-verification.md) に記録する。

新規保存先の列名・先頭行固定・Google画面の表示を確認した。認証・履歴ファイルの権限は、それぞれ所有者1名のみで `shared=false`。応募ファイルのリンク閲覧設定は変更していない。既存 `シート1!A1:Z20` と `sorafes-entry_TEST_v1!A1:G25` のセル値をタブ追加前後で照合し一致した。全使用範囲を照合したという意味ではない。旧Apps Scriptにはアクセス・変更していない。

2026-10-09の再確認で、専用APIは `PHASE4_ENABLED=false`。設定取得・新規保存・更新はすべて `CLOSED` を返し、試験データ14応募・28履歴・56認証イベントは保持されていた。正式応募受付は開始していない。
