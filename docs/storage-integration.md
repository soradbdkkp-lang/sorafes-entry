## 提案する責務分離

入力画面 → 確認用データ → 送信アダプター → 保存側の検証 → 保存先 → 保存結果の応答。

フロントエンドからスプレッドシートへ直接書き込む構成ではなく、保存側で大会設定・募集可否・入力整合を再確認する入口を設ける案とする。Google Sheets + Apps Scriptは候補であり、ブラウザとの通信方式、応答の取得方法、実行権限、リクエスト制限は構成選定時に公式仕様と実機で検証する。画面から秘密の認証キーを配信する方式は採用しない。

既存のreviewDataは確認画面用であり、そのまま公開APIの確定仕様にしない。保存契約では大会識別、応募形式、人数、代表者参照、有効なプレイヤー情報、時間回答、契約バージョン、再送識別情報を整理する。保存側が受信内容の型・人数・選択肢・固定ロール・キラー条件・実績・受付可否を再検証し、対象外の詳細を除外する。

## 閲覧権限の確定判断

応募情報のスプレッドシートは「リンクを知っている全員が閲覧する」とする。アカウントごとの限定共有ではなく、URLが転送された相手も閲覧できる範囲を許容する。これは閲覧の指定であり、リンクを知っている全員への編集権限は付与しない。編集者の指定は未確定。

共有シートには運営アカウントの認証情報・APIキー・編集コード・編集検証情報等の秘密情報を含めない。非表示タブや列を秘密情報のアクセス制御として利用しない。必要な内部情報はリンク閲覧対象から分離した保存先で管理する構成を検討する。抽選方法・基準・内部判断も共有対象に含めない。

フォーム画面や応募用APIから一覧を返す機能は追加しない。共有URLの配布先・配布方法、参加前の情報取扱い案内は別途確認する。公開フォームの入口は応募の新規作成だけを扱い、運営操作・既存応募編集を含めない。

保存先IDや公開エンドポイントは秘密の認証手段として扱わない。運営アカウントの認証情報や編集認証情報、実応募内容はGit・フロントエンド設定・通常ログに保存しない。ログは処理の識別と成否を中心とし、入力内容やX ID・ゲーム内IDを出力しない。

## 保存結果と再送の提案

| 状況 | 画面の動作 |
| --- | --- |
| 送信中 | 送信操作を抑止し、進行中と表示。入力は保持 |
| 保存側で入力不備 | 該当項目を案内し、修正後に再確認 |
| 明確な保存失敗 | 入力を保持し、再試行を案内。受付完了を表示しない |
| 通信切断・応答不明 | 「保存結果を確認できません」と表示。失敗や成功を断定せず、同じ送信識別情報で再確認・再試行 |
| 保存確定 | 保存側から確定応答を得てから受付完了を表示。当選とは区別 |

同じ内容の再試行は同じ送信識別情報として扱い、多重保存を防ぐ案。送信識別情報は編集認証ではない。入力を変更した再送と同じ識別情報で異なる内容が来た場合の扱いを定義する。ページ再読み込み後の復旧、識別情報の有効期間、同時処理の排他、途中保存の復旧は実装前に具体化する。

Phase 4の編集コード導入前に、本番受付を開始しない。Phase 3は架空データのテスト保存までを提案する。

スプレッドシートに保存された応募情報は削除しない。大会開催日を削除期限とせず、大会後も保持する。自動削除・保存期限による削除処理は設けない。集計・エクスポート・バックアップの具体的な運用は未確定。将来の削除は今回の指示から推測して実行しない。
